# 项目实现逻辑与调试复盘

整理日期：2026-10-19。源码基线：`v0.21.0-boot-led-active-low`，提交`cc5a91b`。
本文区分当前启用算法、历史实验和实物证据；不修改固件。部分早期README还保留历史参数，当前行为以实际配置覆盖顺序和源码为准。

## 1. 项目解决什么问题

系统把时钟/闹钟、按键/编码器、OLED、IMU、舵机、双串口及低功耗组织到同一个STM32程序中。
核心控制任务是：IMU固定在舵机驱动的连杆上，编码器设置并确认目标姿态，系统测量连杆相对重力参考的单轴姿态，调整舵机指令，使连杆抵抗底座扰动并保持目标姿态。

必须区分三个量：

| 量 | 含义 | 能否直接代表实物 |
|---|---|---|
| T / target | 希望保持的姿态角 | 是设定值 |
| M / measured | IMU估计的被控连杆姿态 | 是传感器估计，仍有噪声、延迟和安装误差 |
| OUT / SERVO | 发送给舵机的角度指令，经线性换算得到脉宽 | 不是舵机轴角度测量，也不保证机构已到位 |

手动模式设置90°，表示输出约1500µs；HOLD设置90°，表示希望被控机构保持标定参考下的90°姿态。两者不是同一种物理量。SG90内部自行完成位置控制；本项目在它外面又加一层IMU姿态闭环。

如果IMU只装在面包板上，舵机动作不能改变这块IMU的姿态，就不能用同一PID误差闭环控制连杆。那是底座倾角前馈补偿问题，需要不同的模型，不能和当前“IMU装在连杆上”的闭环混用。

| 工作 | 当前周期/方式 |
|---|---|
| TIM2时间基准及按键扫描 | 5ms |

| BLE TRACE | 200ms，约5Hz |

频率要分清：PWM载波频率、控制计算频率、传感器采样频率、界面/日志频率各有用途。把TRACE改快不会自动使控制变快，把PWM载波改快也不等于舵机机械速度变快。

## 3. 基础模块

**按键：** PA0、PA2内部上拉，按下接GND。每5ms扫描，电平需稳定约20ms才切换消抖状态；发布PRESS/SHORT/LONG/RELEASE事件，长按严格大于1秒且只报一次。按键事件队列把“检测输入”和“执行动作”分开，不用delay等待用户松手。

**双键消警：** 报警时只检查消抖后的K1和K2是否都按住，不要求两个PRESS时间戳相同。允许先按住任何一键，再按另一键；单键短按/长按不消警也不操作菜单。消警手势的短按、长按及松开被消耗，两键完全松开后恢复正常操作。停止本次提醒不等于删除或停用闹钟。

**编码器：** PB6/PB7交给TIM4编码器模式，由硬件统计AB相位，软件读取计数差值，默认4计数/格并保留不足一格的余量。无需每个边沿都进中断。编辑值与实际控制值分开，旋转先改草稿，确认后执行。

**RTC与闹钟：** 使用板载32.768kHz LSE。RTC计秒，软件转换时分秒。三个逻辑每日闹钟映射到下一个最近的硬件Alarm事件，同时处理跨午夜、多个同时到点和跳时等情况；不是三个独立RTC硬件闹钟。PB0低有效，活动报警500ms亮/500ms灭。不能把存在备用域接口等同于所有断电/复位情形自动保存全部设置。

**PWM：** 舵机PA8为50Hz，指令映射近似`pulse_us=500+angle*2000/180`，限于500～2500µs。TIM预装载保证稳定周期更新。开机灯PA6现在低有效：3.3V→限流电阻→LED正极，负极→PA6。PWM1输出反相，因此亮度0时输出高、灯灭；亮度100%时输出低、灯亮。呼吸约3秒，从0.5Hz渐快至2Hz，最后熄灭；1kHz是载波，0.5～2Hz是呼吸节奏。

**OLED/I²C：** OLED和IMU共享PB8/PB9，依靠不同地址区分；物理上可通过面包板分线。总线100kHz，任务由状态机推进。OLED只发送变化块，避免每次整屏刷新长期占用总线；初始化、唤醒或恢复时仍需完整重刷。非阻塞只能降低占用，不能消除总线带宽和交易时间。

**通信：** USB为USART1/115200，蓝牙模块串口为USART3/9600；两路独立接收和应答，共用指令执行逻辑。主循环组行，CR/LF/CRLF结尾，严格语法，固定容量队列和非阻塞发送。RTC写入完成后才回复成功，避免后续指令越过尚未完成的改时。PC用后台线程做USB或BLE I/O，Tk主线程更新界面；BLE通知跨包拼行，命令追加CRLF再分片。

**Sleep：** 60秒无操作关闭OLED，普通Sleep保留RTC和定时器等外设；5ms时基仍会唤醒CPU，因此不是深度掉电。第一次按键手势只唤醒，不执行菜单动作。真正Standby是另外一种会复位唤醒的模式，当前未作为默认。没有测量电流，就不能从“用了PWR”直接推出具体省电比例。

## 4. IMU姿态是怎样算出来的

### 4.1 初始化与读数

驱动异步完成上电等待、地址/WHO_AM_I探测、复位、寄存器配置和读取。接受0x68或用户确认的0x70器件ID；I²C地址0x68/0x69与器件ID不是同一个概念。

每次连续读取14字节，包含加速度、温度和三轴角速度。当前加速度量程±2g，对应16384 LSB/g；陀螺仪±1000°/s，对应32.8 LSB/(°/s)。初始化会读回GYRO_CONFIG，必须等于0x10再继续。配置值、量程和换算系数必须一起改；读回一致仍不能独自证明替换模块的物理比例完全正确。

### 4.2 校准

静止采集200次连续合格样本，约2秒，用平均值估计三轴陀螺仪零偏，并记录安装参考姿态。明显运动或不合格采样会重置窗口，所以KEEP STILL不是普通倒计时。

陀螺仪读数减去零偏，可减少积分漂移；记录初始姿态则用于参考角补偿。这两件事不能混称“校准后角度绝对正确”。未完成校准、数据失效或过期时不允许开启HOLD。

### 4.3 安装轴与单轴角度

当前安装映射为：机构`(X,Y,Z)=传感器(X,Z,-Y)`。因此机构Y角速度对应传感器GZ，代码中的D项也使用校准后GZ。显示的GX/GY/GZ保留传感器轴定义，不能只看变量叫GY就当作控制轴。

控制轴重力倾角使用映射后的加速度：

```text
theta_acc = atan2(-ax, az)             // 转为角度
theta_relative = Wrap(theta - theta_zero)
M = 90° + theta_relative
```

这是一项保留正负和越过竖直方向信息的单轴倾角，区别于只在±90°内折返的常规Euler Pitch。它不是完整三维姿态控制；横向偏离设计转轴、动态加速度和重力投影不足都可能使它不可靠。90°参考依赖“校准时连杆确实竖直”的安装条件，传感器不会自动知道连杆和地面的真实夹角。

### 4.4 互补融合

陀螺仪短时响应快，但积分有漂移；加速度计可提供重力方向，但运动时包含额外加速度。代码先积分，再在重力可信时校正：

```text
theta_predict = Wrap(theta_previous + omegaY * dt)
alpha = tau / (tau + dt)
theta = Wrap(theta_predict + (1-alpha) * Wrap(theta_acc-theta_predict))
```

普通tau=0.5秒。这里的0.5秒是重力残差校正时间常数，不是简单地把整个姿态信号延迟0.5秒；陀螺仪预测仍直接推进。

静止加速校正须连续满足约80ms严格条件：角速度各轴≤2°/s，加速度模长约0.97～1.03g，投影充分，重力角波动≤0.2°，采样间隔≤30ms。残差≤2°时才用tau=0.1秒，并限制校正≤6°/s，减少停稳后的慢回落。它不重新标定零偏，也不能把失效数据变有效。

### 4.5 动态重力拒绝与200ms接续

普通可信条件为加速度模长0.8～1.2g，并且选定平面投影平方≥0.04。快速转动可能暂时不满足，不能把此时加速度一律当作重力。

已经校准、有可信历史参考、帧本身可用且陀螺仪不饱和时，可在最长200ms内仅靠角速度接续，可信重力回来后恢复校正。200ms不是整机通信超时：100ms样本过期、单次积分间隔上限和硬异常检查仍分别存在。接续变长提高抗瞬态能力，也增加纯积分误差风险，不是越长越好。

## 5. 当前真正启用的控制算法

### 5.1 参数覆盖要看最后生效值

App_Init先调用Control_DefaultConfig，再覆盖应用参数，之后APP_POSITION_PID_TEST与APP_RATE_PID_TEST继续覆盖。当前有效值如下，不能只读默认函数或某个历史宏：

| 项目 | 有效值 |
|---|---|
| 模式 | PID姿态外环 |
| 轴/反馈方向 | Pitch单轴 / -1 |
| Kp、Ki、Kd | 0.7、8.0、0.005 |
| 积分增益调度 | 关闭，当前Ki常数；历史非线性函数仍保留 |
| 目标范围 | 0～180°，不代表任何底座姿态都机械可达 |
| I项限幅 | ±180°控制贡献，另受输出可达约束 |
| 更新周期 | 至少20ms且新样本 |
| 死区/过渡 | 0.5° / 0.3° |
| D输入 | 选定机构轴的校准角速度，当前为传感器GZ |
| D额外低通 | 关闭，不等于IMU内部DLPF也关闭 |
| D贡献限幅 | ±0.5° |
| D静止抑制 | 原始误差≤0.5°且角速度≤3°/s时D=0 |
| 输出指令范围/限速 | 0～180° / 180°/s |
| 样本过期/控制长间隔保护 | 100ms / 200ms |

### 5.2 开启HOLD

确认传感器有效、已校准且不过期；把当前实测姿态作为初始目标T，把当前舵机指令作为固定偏置u0，I清零。重复发送HOLD ON不会反复重置。这样进入闭环时误差近0，尽量避免突然跳转。开启HOLD锁当前89.7°不等于程序设成90°。

另外，当前UI先将目标保留到0.1°，旋转编码器每格加1°；若起点为89.7°，一般会变90.7°，不是90.0°（到边界截断另论）。这是现有目标编辑规则的限制，不能误称已经支持任意0.1°精确设置；本次学习总结只指出现状，没有替用户修改这项交互。

### 5.3 每轮计算

先算原始误差`e=T-M`。显示和TRACE保存原始e，控制使用死区处理后的ec：

```text
|e| <= 0.5°       : ec = 0
0.5° < |e| < 0.8°: w=(|e|-0.5)/0.3; ec=e*w*w*(3-2*w)
|e| >= 0.8°       : ec = e

P = 0.7 * ec
I_candidate = clamp(I + 8 * ec * dt, -180, +180)
D = clamp(-0.005 * omegaY, -0.5, +0.5)
u_request = u0 + direction * (P + I + D)
```

D还会执行上述静止抑制；I不是直接无条件采用candidate，而要通过抗饱和处理。

P立即响应偏差。I把持续小偏差逐渐变成能抵消底座倾斜的舵机偏置，即使以后e≈0，也保留已有I，不能一到零误差就把I清空。D对测量角速度反馈，主要提供阻尼，不对目标阶跃做差分，减少设定值变化带来的微分冲击。

例：T=90°、M=80°时e=10°，P=7°。direction=-1，因此仅看P会把舵机指令向较小角度调整；此前实测“舵机指令90→100使姿态下降约10°”，所以该方向构成负反馈。最终输出还要经I/D、限幅和限速，不能说它一轮就必定输出83°。

### 5.4 抗积分饱和与输出限制

指令不仅有0～180°边界，也有每轮可移动窗口。20ms时`180°/s * 0.02s = 3.6°`，即使算法要求跳20°，这一轮也最多改约3.6°。

代码先计算本轮积分原本想贡献多少，再只接受当前输出窗口容得下的部分；已有P/D超限不会强行把I反向拉回，反向消除已积累I仍允许。早期整步拒绝方式可能在`Ki*|e|`超过限速时长期不更新I，形成大误差“冻住”。改成接受部分增量，就是解决这一结构性问题，而非只继续增大Ki。

最后将输出限制到范围和每轮窗口，再换算成PWM脉宽。TRACE中的saturated表示请求与受限结果存在差异，可能涉及限速/幅度及积分处理，不是舵机机械堵转传感器。

### 5.5 这是什么PID，不是什么PID

它是固定HOLD入口偏置加PID贡献的姿态外环，不是每轮把完整P+I+D再次累加到上轮输出。历史FOLLOW用于底座传感器跟随映射，DIRECT依赖执行器位置估计，两者代码保留但当前均未启用。当前也不是卡尔曼滤波、完整三维解算或底座前馈控制。

死区内ec=0使P和新增I为0，但已有I保留；若角速度较大，D仍可能动作。0.5～0.8°平滑过渡减少硬切换抽动，也可能牺牲一点末端收敛速度。当前参数Ki固定8，只是ec被平滑缩小；这不等于之前那套按误差调Ki的实验仍开启。

## 6. 保护为什么会“停住不恢复”

IMU无效、样本过期或控制更新长间隔会锁存控制故障，保持最后PWM指令。并非断电、也并非把舵机自动回90°。传感器随后恢复有效，只能更新观测；不会自动重新推动机构。需要先关闭HOLD清故障，确认有效后再开启。

因此出现`FAULT=IMU_INVALID`，随后`RAW VALID=1`并不矛盾：前者是曾经触发并保留的故障，后者是当前这一帧。真正要看`IMU FAULT ?`里的首次故障快照。当前移除的是SYS RESET诊断，不是这些IMU有效性或HOLD保护。

## 7. 调试问题复盘

| 现象 | 证据/判断 | 处理与结论 |
|---|---|---|
| ST-Link异常、发热、下载未成功 | 用户报告；后来解决 | 当时未采到足够电气证据，不能认定由固件造成，也不能追认具体硬件根因 |
| OLED花屏 | 重接线后报告 | 总线/供电/接线都需核查；未有足够证据唯一定位，不把某次刷新优化当作花屏根因证明 |
| IMU FAULT/STARTING，无数据 | WHO NACK、WHO ID=70 | 修正兼容ID，保留明确NACK/超时/读回错误诊断；0x70不等于I²C地址，间歇NACK不能仅靠放行ID解决 |
| CAL KEEP STILL，HOLD不可开 | 校准未完成，随后显示姿态角后HOLD解决 | 静置完成连续200帧校准；陀螺仪有数字不代表姿态可用 |
| 舵机嗡响但不转 | 手动输出已有合理脉宽；用户确认是电源原因 | 独立合适5V并共地；先验证电源和手动模式，再怀疑姿态PID |
| USB无回复 | 用户确认TX/RX接反；后来出现ERR SYNTAX | 纠正交叉接线，严格语法和实际换行；串口通了与命令合法是两层问题 |
| BLE已连接却无回复 | PC显示写入，用户后来确认接错线 | 纠正HC-04 TXD→PB11、RXD→PB10；BLE连接成功不代表模块到MCU链路成功 |
| 上位机找不到端口 | 明确ModuleNotFoundError: serial | 给启动上位机的同一Python补装依赖，随后枚举到CH340 COM5；不是GPIO或PWM问题 |
| 脚本找不到/CSV找不到 | 在错误工作目录或只给了相对路径 | 使用实际文件绝对路径；看到HTML/JSON输出后才算分析完成 |
| 第一键唤醒兼执行菜单 | 同一手势同时作唤醒与业务事件 | consumed_keys消耗整次唤醒动作，松手后下一次才正常操作 |
| IMU在面包板上时PID跑端点 | 舵机动作不改变传感器姿态 | 明确被控对象，后续IMU固定到连杆；闭环反馈必须能反映执行器的作用 |
| 姿态轴/方向混淆，90°附近异常 | 通过手动90→100→90核对轴和符号 | 选单轴倾角、安装坐标映射及direction=-1；先测反馈方向，再调增益 |
| HOLD目标只在90～100附近 | 历史诊断模式限制过小 | 当前目标与输出全范围0～180，仍受真实机械行程限制 |
| 静止或到位后小幅左右摆 | 关闭I等对照仍有摆；纯P阶段较平稳但有残差；TRACE见死区边沿输出跳变 | 不能全归于积分；引入直接角速度D、贡献限幅与静止抑制、平滑P/I死区。不同阶段证据支持不同因素 |
| 大角度后间歇慢挪 | 误差靠小积分缓慢消除，且存在限速/测量尾段 | 提高积分、尝试DIRECT及速度反馈、修复部分积分接受；当前仍有动态滞后，不能宣称所有动作一步到位 |
| MANUAL实物已停，M仍慢回落 | 用户确认连杆停住，细采样看到约0.7°尾段 | 将估计误差与真实机械运动分开；加严格静止门控的小残差快速校正 |
| 快速转动后IMU_INVALID | 快照AXIS_PROJECTION，原始加速度曾明显偏离静止1g | 动态可信重力拒绝时限时陀螺接续；部分静止异常原始帧的硬件/采样根因未最终证明 |
| 延长接续后仍故障 | GRAVITY_TIMEOUT，REFAGE=110超过当时100ms | 经用户批准增加到200ms，仍保留通信/过期/饱和保护 |
| 又出现GYRO_RANGE | 故障GYROCLIP=1 | 从±500增到±1000°/s并同步比例、配置读回、首次故障三轴原始值；后续一轮70.48秒记录无故障，不等于永不失效 |
| 大误差但视频看着正常 | CSV与视频来自两次不同测试，后来用户确认存在控制慢 | 不能跨两次试验对齐因果；同步采集并标记停止时刻，观察方向/角度刻度 |
| 小抖动归因混乱 | 某CSV底座一直被手动翻转直到末尾 | 动作段与固定静止段分开；手抖是扰动，不等同控制器自激 |
| 双键像重启、报警灯变暗 | 一根手指按时出现，两根手指分别按正常 | 说明与按压方式相关；具体松接/受力/供电或复位原因未测定。诊断版曾加入，用户要求移除；不可写成“已证明软件无关/已证明某根线短路” |
| LED接法变化 | 用户最终确认正极VCC、负极PA6且不常亮 | 低有效PWM，保留呼吸后灭；不能误改成正负直接跨电源的常亮灯 |
| 页面放大模糊 | Tk低DPI窗口可能被Windows整体缩放 | 系统DPI感知在Tk创建前启用，字体与像素布局分别缩放；不宣称完整混合DPI跨屏支持 |

## 8. 控制方案演进中学到了什么

1. 初期完整PID先可用；提高限速后首轮感觉更快，随后发现小摆动，不能用一次主观评价完成验收。
2. 非线性积分、减Ki、关I、减Kp、纯P是诊断过程；纯P平稳但有持续偏差，说明“平稳”和“无静差”不是同一目标。
3. 慢积分和硬死区有稳定收益，也会留下慢挪和尾段误差；加大Ki不能解决反馈方向错、传感器装错位置或数据失效。
4. DIRECT依赖执行器位置估计，模型时间常数失配可能产生明显过冲；它不是知道舵机真实位置。失败模型候选也要保留，而不是把不合格结果隐藏。
5. 固定偏置PI+D配合直接角速度反馈成为当前活动方案，但原宽范围延迟模型仍有未通过情形，不能把较快假设下的通过扩大成所有硬件的保证。
6. “小动作慢转通过”不等于“突然大转通过”；快速运动暴露的是重力可信性和陀螺量程，而不一定是P太小。
7. 修复整步拒绝积分造成冻结，是算法结构修复；放宽量程和短时接续，是测量范围与有效性策略；两者不能混称一次PID调参。
8. 最新持续运动记录3525帧/70.48秒无故障，但目标89.8°时记录M约16.9～152.2°，动态最大误差73°；431帧约12.2%显示受限且每20ms变约3.6°，与180°/s软件限速吻合。用户直到末尾才停下，不能据此给出可靠停稳恢复时间。这是仍存在动态性能空间的证据，不是完整实物验收。

## 9. 下一次如何做有解释力的试验

每轮记录Git标签/烧录版本、安装方式、电源、目标、动作时间和CSV通道。只改一个参数或一个明确算法问题。先固定底座MANUAL 90→100→90核对动作、方向、估计响应，再进入HOLD。

把“全程固定静止”“小角度移动后固定”“持续往返跟踪”“快速大扰动/限位”分成不同测试。用固定支撑或清楚的停止标记，尽量同步视频和CSV；手的停止时间不清楚，就不计算确定恢复时间。

分别观察：静止误差与抖动、运动跟踪误差、停止后的超调、进入误差带并持续保持的时间、故障和限速比例。约定±1°或±2°、保持多久、事件起点是什么，再谈是否提速。持续运动时的大误差不等于停止后的过冲。

出现异常先保留现场，查SERVO HOLD ?、IMU RAW ?、IMU FAULT ?，再决定是否关闭HOLD。当前瞬时VALID=1不能代替故障瞬间快照。COM打开/蓝牙写入成功也不能代替设备OK应答或实物动作确认。

Git记录、ZIP备份、主机测试、模型筛选、实物验收分别回答不同问题：版本能追溯、代码符合局部契约、某些假设下性能如何、真实设备表现如何；它们不能互相替代。

## 10. 建议的源码阅读顺序

先Application/main.c看总入口，再Application/app.c的Sample/Keys/App_Init/App_Process；读app_config.h后务必核对App_Init覆盖顺序。然后读IMU/imu_config.h与imu_core.c，再读Control/control.h和control.c的StartHold/Update。最后读ui_core、protocol、rtc_core和pc_monitor。

学习时可以追问每个量：来自哪里、单位是什么、在哪个坐标系、多久更新、失效时怎么办、谁能修改它。特别注意：姿态角不是PWM指令，当前有效不是历史未出错，测试通过不是实物性能已达标。
